# ADR-0001. Три независимых слоя образов: runtime → ядро → модпак

Статус: **принято** · 14.09.2026, реализовано этапами 1–3 (15.09.2026)

## Контекст

Образ `kyuz0/amd-strix-halo-comfyui` клонирует master ComfyUI при сборке и больше его не меняет.
ComfyUI выпускает релиз раз в 2–3 дня; за 4 недели жизни образа мы отстали на 14 релизов.
Обновить ComfyUI внутри образа нельзя (`/opt/ComfyUI` не git-репозиторий, Manager отказывается),
а новый образ kyuz0 меняет заодно torch и ROCm — невозможно понять, что сломало сборку.
Требование пользователя — быстро переходить на последние версии ComfyUI.

## Решение

Три `Containerfile`, каждый `FROM` предыдущего:

1. **runtime** — ОС, Python, torch/ROCm под gfx1151; меняется редко и осознанно;
2. **ядро** — ComfyUI по тегу/коммиту (`ARG COMFYUI_REF`) с его requirements и патчами;
3. **модпак** — ноды из lock-файла, их зависимости и патчи; тег ядра — параметр сборки.

Данные (модели, user, input, output, кэши) монтируются и в образы не входят.

## Рассмотренные варианты

| Вариант | Почему нет |
|---|---|
| `FROM kyuz0` и замена `/opt/ComfyUI` поверх | тянем чужой ComfyUI, ноды и Fedora prerelease; `latest` меняется без нашего ведома; обновление torch всё равно привязано к автору |
| ComfyUI с хоста, монтируется в контейнер | зависимости ComfyUI меняются каждый релиз, код и venv расходятся; откат кода не откатывает пакеты. Оставлено как dev-режим для отладки |
| Один образ со всем, пересборка целиком | каждое обновление ComfyUI перекачивает гигабайты torch; нет изоляции причин поломок |

## Последствия

- Обновление ComfyUI = пересборка тонкого слоя за минуты + пересборка модпака поверх.
- Откат = перетег образа; бэкап `user/` обязателен из-за миграций `comfyui.db`.
- Рецепт runtime поддерживаем сами; kyuz0 остаётся источником проверенных версий и флагов.
- Нужен собственный инструмент `tools/comfy` и тесты (см. [comfyui-updates.md](../comfyui-updates.md)).
